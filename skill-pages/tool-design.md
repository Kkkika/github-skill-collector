# 代理工具设计

工具是代理与世界互动的主要机制。它们定义了确定性系统与非确定性代理之间的契约。与为开发人员设计的传统软件 API 不同，工具 API 必须为能够推理意图、推断参数值并从自然语言请求生成调用的语言模型而设计。糟糕的工具设计会产生任何提示工程都无法修复的故障模式。有效的工具设计遵循特定的原则，这些原则考虑了代理如何感知和使用工具。

## 何时激活

在以下情况时激活此技能：
- 为代理系统创建新工具时
- 调试与工具相关的故障或误用时
- 优化现有工具集以获得更好的代理性能时
- 从头开始设计工具 API 时
- 评估用于代理集成的第三方工具时
- 在代码库中标准化工具约定时

## 核心概念

工具是确定性系统与非确定性代理之间的契约。整合原则指出，如果人类工程师无法明确说明在给定情况下应使用哪个工具，那么就不能指望代理做得更好。有效的工具描述是塑造代理行为的提示工程。

关键原则包括：回答“是什么、何时、返回什么”的清晰描述；平衡完整性和令牌效率的响应格式；启用恢复的错误消息；以及减少认知负荷的一致约定。

## 详细主题

### 工具-代理接口

**工具作为契约**
工具是确定性系统与非确定性代理之间的契约。当人类调用 API 时，他们理解契约并发出适当的请求。代理必须从描述中推断契约，并生成符合预期格式的调用。

这种根本差异需要重新思考 API 设计。契约必须毫不含糊，示例必须说明预期模式，错误消息必须指导更正。工具定义中的每一个歧义都会成为潜在的故障模式。

**工具描述作为提示**
工具描述被加载到代理上下文中，共同引导行为。描述不仅仅是文档——它们是塑造代理如何推理工具使用的提示工程。

像“搜索数据库”这样带有隐晦参数名称的糟糕描述迫使代理进行猜测。优化的描述包括使用上下文、示例和默认值。描述回答了：工具做什么，何时使用它，以及它产生什么。

**命名空间和组织**
随着工具集合的增长，组织变得至关重要。命名空间将相关工具分组在通用前缀下，帮助代理在正确的时间选择适当的工具。

命名空间在功能之间创建了清晰的边界。当代理需要数据库信息时，它会路由到数据库命名空间。当它需要网络搜索时，它会路由到网络命名空间。

### 整合原则

**单一综合工具**
整合原则指出，如果人类工程师无法明确说明在给定情况下应使用哪个工具，那么就不能指望代理做得更好。这导致了对单一综合工具的偏好，而不是多个狭窄的工具。

与其实现 `list_users`、`list_events` 和 `create_event`，不如实现 `schedule_event` 来查找可用性并进行调度。综合工具在内部处理完整的工作流程，而不需要代理链接多个调用。

**为什么整合有效**
代理的上下文和注意力有限。集合中的每个工具都在工具选择阶段争夺注意力。每个工具都会增加消耗上下文预算的描述令牌。重叠的功能会造成关于使用哪个工具的歧义。

整合通过消除冗余描述来减少令牌消耗。它通过让一个工具覆盖每个工作流程来消除歧义。它通过缩小有效工具集来降低工具选择的复杂性。

**何时不整合**
整合并不总是正确的。具有根本不同行为的工具应保持分离。在不同上下文中使用的工具受益于分离。可能独立调用的工具不应被人为捆绑。

### 架构缩减

整合原则如果发挥到极致，会导致架构缩减：移除大多数专用工具，转而使用原始的、通用的能力。生产证据表明，这种方法可以胜过复杂的多工具架构。

**文件系统代理模式**
与其构建用于数据探索、模式查找和查询验证的自定义工具，不如通过单个命令执行工具提供直接的文件系统访问。代理使用标准的 Unix 实用程序（grep, cat, find, ls）来探索、理解和操作您的系统。

这之所以有效，是因为：
1. 文件系统是模型深入理解的经过验证的抽象
2. 标准工具具有可预测的、文档齐全的行为
3. 代理可以灵活地链接原语，而不是受限于预定义的工作流程
4. 文件中良好的文档取代了对摘要工具的需求

**何时缩减优于复杂性**
缩减在以下情况下有效：
- 您的数据层文档齐全且结构一致
- 模型具有足够的推理能力来驾驭复杂性
- 您的专用工具是在限制而不是赋能模型
- 您花在维护脚手架上的时间比改善结果的时间还多

缩减在以下情况下失败：
- 您的底层数据混乱、不一致或文档记录不佳
- 该领域需要模型缺乏的专业知识
- 安全约束要求限制代理可以做的事情
- 操作确实复杂，并受益于结构化的工作流程

**停止限制推理**
一个常见的反模式是构建工具来“保护”模型免受复杂性的影响。预过滤上下文、限制选项、将交互包装在验证逻辑中。随着模型的改进，这些护栏通常会成为累赘。

要问的问题是：您的工具是在启用新功能，还是在限制模型自己可以处理的推理？

**为未来的模型构建**
模型的改进速度快于工具的跟进速度。为今天的模型优化的架构可能对明天的模型来说限制过多。构建能够从模型改进中受益的最小架构，而不是锁定当前限制的复杂架构。

请参阅 [架构缩减案例研究](./references/architectural_reduction.md) 了解生产证据。

### 工具描述工程

**描述结构**
有效的工具描述回答四个问题：

工具做什么？清晰、具体的能描述。避免使用“有助于”或“可用于”等模糊语言。确切说明工具完成了什么。

何时应该使用它？具体的触发器和上下文。包括直接触发器（“用户询问价格”）和间接信号（“需要当前市场汇率”）。

它接受什么输入？带有类型、约束和默认值的参数描述。解释每个参数控制什么。

它返回什么？输出格式和结构。包括成功响应和错误条件的示例。

**默认参数选择**
默认值应反映常见用例。它们通过消除不必要的参数规范来减轻代理负担。它们可以防止因省略参数而导致的错误。

### 响应格式优化

工具响应大小显着影响上下文使用。实现响应格式选项使代理能够控制详细程度。

简洁格式仅返回基本字段，适用于确认或基本信息。详细格式返回包含所有字段的完整对象，适用于决策需要完整上下文的情况。

在工具描述中包含有关何时使用每种格式的指导。代理学习根据任务要求选择适当的格式。

### 错误消息设计

错误消息服务于两个受众：调试问题的开发人员和从故障中恢复的代理。对于代理，错误消息必须是可操作的。它们必须告诉代理出了什么问题以及如何纠正它。

设计能够启用恢复的错误消息。对于可重试的错误，包括重试指导。对于输入错误，包括更正后的格式。对于缺失数据，包括所需内容。

### 工具定义模式

在所有工具中使用一致的模式。建立命名约定：工具名称使用动词-名词模式，跨工具使用一致的参数名称，一致的返回字段名称。

### 工具集合设计

研究表明，工具描述重叠会导致模型混淆。更多的工具并不总是导致更好的结果。一个合理的指导方针是大多数应用程序使用 10-20 个工具。如果需要更多，请使用命名空间来创建逻辑分组。

实现帮助代理选择正确工具的机制：工具分组、基于示例的选择，以及带有路由到专用子工具的伞形工具的层次结构。

### MCP 工具命名要求

当使用 MCP（Model Context Protocol）工具时，始终使用完全限定的工具名称以避免“找不到工具”错误。

格式：`ServerName:tool_name`

```python
# 正确：完全限定名称
"Use the BigQuery:bigquery_schema tool to retrieve table schemas."
"Use the GitHub:create_issue tool to create issues."

# 错误：未限定名称
"Use the bigquery_schema tool..."  # 在有多个服务器时可能会失败
```

如果没有服务器前缀，代理可能无法定位工具，尤其是在有多个 MCP 服务器可用时。建立包含服务器上下文的所有工具引用的命名约定。

### 使用代理优化工具

Claude 可以优化自己的工具。当给出工具和观察到的故障模式时，它会诊断问题并提出改进建议。生产测试表明，这种方法通过帮助未来的代理避免错误，将任务完成时间减少了 40%。

**工具测试代理模式**：

```python
def optimize_tool_description(tool_spec, failure_examples):
    """
    Use an agent to analyze tool failures and improve descriptions.
    
    Process:
    1. Agent attempts to use tool across diverse tasks
    2. Collect failure modes and friction points
    3. Agent analyzes failures and proposes improvements
    4. Test improved descriptions against same tasks
    """
    prompt = f"""
    Analyze this tool specification and the observed failures.
    
    Tool: {tool_spec}
    
    Failures observed:
    {failure_examples}
    
    Identify:
    1. Why agents are failing with this tool
    2. What information is missing from the description
    3. What ambiguities cause incorrect usage
    
    Propose an improved tool description that addresses these issues.
    """
    
    return get_agent_response(prompt)
```

这创建了一个反馈循环：使用工具的代理生成故障数据，代理随后使用这些数据来改进工具描述，从而减少未来的故障。

### 测试工具设计

根据标准评估工具设计：无歧义性、完整性、可恢复性、效率和一致性。通过呈现具有代表性的代理请求并评估生成的工具调用来测试工具。

## 实践指南

### 要避免的反模式

模糊的描述：“在数据库中搜索客户信息”留下了太多未回答的问题。

晦涩的参数名称：名为 x、val 或 param1 的参数迫使代理猜测含义。

缺少错误处理：使用通用错误失败的工具不提供恢复指导。

不一致的命名：在某些工具中使用 id，在其他工具中使用 identifier，在另外一些工具中使用 customer_id 会造成混淆。

### 工具选择框架

在设计工具集合时：
1. 识别代理必须完成的独特工作流程
2. 将相关操作分组为综合工具
3. 确保每个工具都有清晰、明确的用途
4. 记录错误情况和恢复路径
5. 使用实际的代理交互进行测试

## 示例

**示例 1：设计良好的工具**
```python
def get_customer(customer_id: str, format: str = "concise"):
    """
    Retrieve customer information by ID.
    
    Use when:
    - User asks about specific customer details
    - Need customer context for decision-making
    - Verifying customer identity
    
    Args:
        customer_id: Format "CUST-######" (e.g., "CUST-000001")
        format: "concise" for key fields, "detailed" for complete record
    
    Returns:
        Customer object with requested fields
    
    Errors:
        NOT_FOUND: Customer ID not found
        INVALID_FORMAT: ID must match CUST-###### pattern
    """
```

**示例 2：糟糕的工具设计**

此示例演示了几种工具设计反模式：

```python
def search(query):
    """Search the database."""
    pass
```

**此设计的问题：**

1. **名称模糊**：“search”是模棱两可的——搜索什么，为了什么目的？
2. **缺少参数**：什么数据库？查询应该采用什么格式？
3. **没有返回描述**：此函数返回什么？列表？字符串？错误处理？
4. **没有使用上下文**：代理何时应该使用此工具而不是其他工具？
5. **没有错误处理**：如果数据库不可用会发生什么？

**故障模式：**
- 代理可能会在应该使用更具体的工具时调用此工具
- 代理无法确定正确的查询格式
- 代理无法解释结果
- 代理无法从故障中恢复

## 准则

1. 编写回答“是什么、何时、返回什么”的描述
2. 使用整合来减少歧义
3. 实现响应格式选项以提高令牌效率
4. 设计用于代理恢复的错误消息
5. 建立并遵循一致的命名约定
6. 限制工具数量并使用命名空间进行组织
7. 使用实际的代理交互测试工具设计
8. 根据观察到的故障模式进行迭代
9. 质疑每个工具是在赋能还是限制模型
10. 优先选择原始的、通用的工具，而不是专用的包装器
11. 投资于文档质量而不是工具的复杂性
12. 构建能够从模型改进中受益的最小架构
